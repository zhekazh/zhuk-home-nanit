# Перевірки

Перевірки мають три рівні, і вони відповідають на різні питання.

| Рівень | Питання | Потрібен макет? |
| --- | --- | --- |
| Монітор порту | «плата взагалі відгукується?» | так |
| Автопрогін `hw_test` | «які модулі живі й що з ними не так?» | так |
| Тести на комп'ютері | «чи не зламала правка логіку?» | ні |

Над цими трьома стоїть одне правило: **довіряти тільки тому, що можна зміряти**.
Прошивка звітує `ok` там, де немає зворотного зв'язку — `TEST fan,run` поверне успіх і з
від'єднаним двигуном, бо це «команду виконано», а не «вал обертався». Тому перевірки
віддають числа: кут, кроки, мілісекунди, розкид, фронти. Слово «ok» без числа означає лише,
що прошивка дійшла до кінця процедури.

## Перша перевірка через монітор порту

Монітор порту: **115200 бод**, кінець рядка **NL**. Після старту має з'явитися
`# Zhuk Home 0.1.0 ready`.

Команди з USB можна набирати **без контрольної суми**. Число після назви команди — її номер,
будь-який від 1 до 65535.

| Команда | Що перевірити |
| --- | --- |
| `$PING,1` | відповідь `$ACK,1*…` |
| `$DBG,2,1` | раз на секунду йдуть кадри `SEC`, `ENV`, `DEV`, `PRK`, `SYS`. Вимкнути: `$DBG,3,0` |
| `$GET,4,hw` | стан усіх модулів: `ok`, `err` або `none` (ще не перевірявся) |
| `$SVC,5,1` | сервісний режим, на екрані `SERVICE` |
| `$TEST,6,servo,open` / `$TEST,7,servo,close` | штора відкривається й зачиняється |
| `$TEST,8,gate,open` / `$TEST,9,gate,close` | шлагбаум піднімається й опускається |
| `$TEST,10,fan,run` | вентилятор крутиться 3 с |
| `$TEST,11,tlight,cycle` | світлофор: червоний, жовтий, зелений |
| `$TEST,12,rgb,r` (`g`, `b`) | RGB світиться червоним (зеленим, синім) |
| `$TEST,13,buzzer,melody` | зумер грає три ноти |
| `$TEST,14,tm1637,all` | на дисплеї паркінгу `8888` |
| `$TEST,15,dht,read` | `TR,15,dht,ok,<°C>,<%>,<мс>` |
| `$TEST,16,sonar,read` | `TR,16,sonar,ok,<см>,…` |
| `$TEST,17,pir,wait` | протягом 15 с пройдіть перед датчиком → `TR,17,pir,ok,…` |
| `$SVC,18,0` | вихід із сервісного режиму |

Рухомі частини (`servo`, `gate`, `fan`, `tlight`, `rgb`) вимагають сервісного режиму, а
перевірки датчиків — знятої охорони: інакше ваш власний помах рукою став би тривогою.

## Автопрогін на макеті

Скрипт говорить із платою тим самим протоколом, що й ESP, але через USB, і сам звіряє
відповіді.

```sh
sh nanit/hw_test/run.sh                 # усе, крім перевірок, що потребують ваших дій
sh nanit/hw_test/run.sh --interactive   # разом із датчиками, клавіатурою й охороною
sh nanit/hw_test/run.sh --no-motion     # без руху механіки
```

Без `--no-motion` скрипт рухає штору й шлагбаум, вмикає вентилятор і звук, тому спершу питає
підтвердження. Режим `--interactive` просить вас пройти перед датчиком руху, плеснути в
долоні, піднести руку до вікна, накрити датчик світла й натиснути клавіші, а наприкінці
перевіряє постановку на охорону з кодом (типово `1234`, інший задається через `--pin`).

Коли треба перевірити щось одне:

```sh
sh nanit/hw_test/run.sh --only hw,passive        # лише вибрані секції
sh nanit/hw_test/run.sh --sensor sound           # лише датчик звуку
sh nanit/hw_test/run.sh --sensor pir,wsens,ldr   # лише ці датчики
```

Назви секцій: `link`, `status`, `settings`, `hw`, `passive`, `actuators`, `sensors`,
`gesture`, `keypad`, `security`. Назва датчика сама вмикає секцію `sensors`, тож `--interactive` у цьому
разі не потрібен.

> **Монітор порту в Arduino IDE має бути закритий:** послідовний порт тримає лише одна
> програма. Весь обмін пишеться у `hw_test.log` поруч зі скриптом.

### Дві пастки, на які вже витрачено час

**Плата не перезавантажується між запусками скриптів.** `stty -hupcl` тримає DTR, тож стан у
RAM — увімкнений `DBG`, кеш команд, активний `WATCH` — переживає закриття порту. Ознака
справжнього свіжого старту — рядок `# Zhuk Home … ready`. Без нього ви говорите з платою,
яка пам'ятає попередній сеанс.

**Кадри стану надійніші за події.** Події вимагають підтвердження й можуть застрягти в черзі;
кадри `SEC`, `DEV`, `PRK` ідуть щосекунди безумовно. Якщо перевірка чекає на подію й не
дочекалась — перевірте стан у кадрі, перш ніж шукати проблему в залізі.

## Тести на комп'ютері

```sh
sh nanit/host_test/run.sh
sh esp/host_test/run.sh
```

Потрібен лише `g++`: заліза, мережі й модуля тести не вимагають. Разом — **461 перевірка**
(Nanit 186, ESP 275).

**Тести Nanit** перевіряють протокол, охорону, налаштування, сервісний режим і перевірки
модулів із заглушками замість заліза. Окремо там зібрано регресії на дефекти, які колись
коштували найдорожче: чи не оживає прострочений строк після переповнення `millis()`, чи не
сповзає штора під захистом від защемлення, чи не підніметься будинок під охороною зі сміття
в EEPROM.

**Тести ESP** перевіряють те, що на макеті майже не видно, а ламається тихо:

- `link` — CRC і розбір кадрів (битий, без зірочки, з огризком CRC, задовгий), черга команд
  із повторами тим самим номером і таймаутом, підтвердження подій, відмова писати кадр, який
  не влазить у буфер передачі цілком;
- `logbuf` — кільце вебконсолі: буфер не росте, рядок обрізається під слот, перенесення рядка
  не розриває кадр у порту;
- `hub` — віддача знімка стану новій сторінці, журнал подій із часом, розбір команд від браузера й
  відсіювання сміття (`$` і `*` розсипали б кадр до Nanit);
- `store` — налаштування модуля у файловій системі: збереження, читання, перевірка запису;
- `evstore` — кільцевий журнал у файлі. Перезапуск ESP тут справжній: бінарник запускається
  кілька разів, і позицію запису модуль щоразу шукає в самому файлі.
